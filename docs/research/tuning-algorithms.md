# Tuning Algorithms — Cross-Project Synthesis

This document synthesizes algorithm-level findings across all reference projects (see [`reference-analysis.md`](./reference-analysis.md) for per-project detail) to inform our own implementation of step-response extraction, event detection, FFT/noise analysis, tracking metrics, and PID recommendation logic — written **before** implementing any of it, per the project brief.

## Step-Response Approaches Found

| Project | Method | Strength | Weakness |
|---|---|---|---|
| PIDtoolbox (`PTstepcalc.m`) | Heuristic "snap-release" detection: smoothed derivative of \|setpoint\| flags stick-deceleration events; extracts/normalizes/QC-gates a ~400ms window of PID error after each event. | Simple, interpretable, works on any log with hard maneuvers. | Only samples tail-ends of aggressive maneuvers; no formal system-ID grounding; author's own comment calls it a stopgap and points to deconvolution as the better approach. |
| PID-Analyzer (Plasmatree) | **Wiener deconvolution**: continuous 1s sliding windows (Hann, ~16x overlap) across the whole flight; `H*/(\|H\|²+1/SNR)` per window with a synthetic frequency-dependent SNR mask (25Hz cutoff); `cumsum()` of deconvolved impulse response → step response. Density/mode-seeking weighted average across all windows for robustness. | Technically strongest method studied — proper system-ID via deconvolution, not maneuver-dependent. Runs continuously, doesn't need explicit event detection. | No event/quality gating at all (only a min-sample-count low/high split at 500°/s); setpoint reconstruction (when not directly logged) uses a hard-coded, version-specific Betaflight P-scaling constant (`0.032029`); tuned to 2017-era Betaflight (pre-RPM-filter, pre-feedforward) spectra. |
| SmartTune CLI | Reimplements PIDtoolbox's `PTstepcalc.m` lineage but with proper **Wiener-regularized FFT deconvolution**: SP-amplitude gating (20-500°/s), zero-padded FFT, λ=1e-4×max(Pxx) regularization, steady-state QC (mean in [0.5,3.0] over 200-500ms), segment averaging. | Combines PIDtoolbox's segment-selection instinct with PID-Analyzer's deconvolution rigor; actively maintained; MIT-licensed and directly reusable. | Upstream project's own roadmap admits this hasn't been cross-validated against Blackbox Explorer's step-response output — treat numeric output as unverified until we validate it ourselves. |
| FPVPIDlab ("PID Tune" mode) | Step-response extraction (lineage: Plasmatree technique) feeding rise time, overshoot%, settling time, ringing (zero-crossings), steady-state error, FF-energy-ratio as scalar metrics. | Only project studied that converts the step-response curve into the **scalar metrics** (overshoot%, rise time, etc.) that neither PIDtoolbox nor PID-Analyzer compute at all. | Self-described as not yet hardware-validated; specific numeric thresholds are project claims, not independently verified. |
| FPVPIDlab ("Flash Tune" mode) | Parallel FFT + Wiener deconvolution → frequency-domain metrics (phase margin, bandwidth, DC gain), gated by a stick-band coherence check (coherence <0.5 disables the rule for that axis/segment). | Frequency-domain view catches issues a time-domain step response can miss; coherence gating is a genuinely good idea for rejecting untrustworthy segments. | Same trust caveat as above. |
| `bf_controller_tuning` / official 2026 Betaflight autotune | Chirp excitation (0.2–600Hz sweep injected into setpoint over ~20s) → frequency response (Bode plots, sensitivity functions) via proper system identification. | Most rigorous system-ID approach studied; official Betaflight is investing in this direction. | Requires a dedicated logging flight with the chirp injected — not usable on arbitrary/existing logs. Official implementation's automatic-fix half has documented failures (zeroed pitch gain) even though the measurement half works. |

**Our approach**: Implement Wiener deconvolution (PID-Analyzer/SmartTune lineage) as the primary step-response method — it's the technically strongest and doesn't depend on maneuver-hunting. Layer PIDtoolbox-style event/amplitude gating on top (SmartTune's 20-500°/s SP-amplitude gate is a good starting point) to discard low-quality segments rather than deconvolving everything blindly. Compute the scalar metrics FPVPIDlab produces (overshoot%, rise time, settling time, ringing, steady-state error) on top of our extracted curve, since none of the primary references (PIDtoolbox, PID-Analyzer) compute these at all. Prefer reading a directly-logged `setpoint[]` field over reconstructing it from `axisP`+gyro; only fall back to reconstruction with a firmware-version-aware P-scaling factor when `setpoint[]` is absent from the log.

## Event Detection Approaches

- **PIDtoolbox**: `stickAcc = smooth(diff(abs(setpoint)), lowess)`; flag samples where `stickAcc < -decelerationThreshold`; dedupe events closer than 1000ms; QC-gate each candidate window (must dip below a floor, must not overshoot a ceiling, must rise past 0.2 early on).
- **PID-Analyzer**: effectively none — continuous windowing, only a post-hoc min-sample-count gate on high-vs-low stick input (500°/s split), and exclusion of near-zero-input windows (<20°/s) from averaging.
- **SmartTune CLI**: SP-amplitude gating at the segment level (20-500°/s) before deconvolution — a middle ground between PIDtoolbox's strict event detection and PID-Analyzer's "deconvolve everything."
- **FPVPIDlab (Flash Tune)**: stick-band coherence check (<0.5 disables the rule for that axis/segment) — rejects segments where measured input/output aren't well-correlated, regardless of amplitude.
- **PIDtoolbox (noise/tracking)**: a *different* segment-selection strategy for "quiet" sampling — cross-axis simultaneous gate (`|setpoint|` AND `|PIDerror|` below a threshold on **all three axes at once**), not literally stick-idle.

**Our approach**: Use SmartTune's amplitude-gating as the baseline pre-filter for step-response segments, and add FPVPIDlab's coherence check as a secondary quality gate. For noise/tracking analysis, adopt PIDtoolbox's cross-axis quiet-sample gate rather than requiring literal stick-centered idle.

## FFT / Frequency-Domain Approaches

- **PIDtoolbox (`PTthrSpec.m`)**: the most fully-specified and portable algorithm found. 200ms non-overlapping segments across the whole flight; each segment tagged with its mean throttle; pooled into 100 throttle bins with **±6% overlap** (deliberate smoothing); Hann-windowed FFT magnitude per segment; averaged per bin; final 100×(N/2+1) matrix box-smoothed in 2D. Produces the classic throttle-vs-frequency noise heatmap. Difference-spectrograms (two tunes, or pre/post-filter) are just element-wise matrix subtraction.
- **PID-Analyzer**: `rfft`-based spectral analysis of gyro/D-term-error/debug channel across throttle bins (via `hist2d`), producing a `filter_trans = noise_gyro / noise_debug` ratio — an estimated filter transmission curve, weighted by the throttle-usage histogram.
- **SmartTune CLI**: generic per-axis gyro FFT (Hann window, configurable overlap), takes the **max envelope across all 3 gyro axes** (not throttle-binned — single averaged spectrum), classifies peaks into motor/prop-blade-pass/structural-resonance/high-freq-resonance bands with harmonic-ratio (2x/3x) inference. Peak detection via `scipy.signal.find_peaks` (height=noise_floor+30dB, prominence=15, distance=3), noise floor = median of the magnitude spectrum, with a pure-numpy fallback already implemented.
- **FPVPIDlab (Flash Tune)**: same FFT+deconvolution family, adds phase-margin/bandwidth/DC-gain metrics gated by coherence.

**Our approach**: Implement PIDtoolbox's throttle-binned heatmap approach (it's the most complete and the de-facto community-standard visualization) using `scipy.signal.windows.hann` + `np.fft.rfft` per 200ms segment, throttle-binned with overlap, `scipy.ndimage.uniform_filter` for 2D smoothing — matching the spec's requirement that our broad interpretation should agree with PIDtoolbox on the same log. Adopt SmartTune's peak-classification/harmonic-ratio logic (with its numpy fallback, so we can drop scipy on the Pi if needed) for identifying *what* a given noise peak likely is (motor, prop, structural). Adopt PID-Analyzer's filter-transmission-ratio concept (gyro/pre-filter-debug spectrum ratio) for filter-effectiveness assessment.

## Noise Metrics

- **D-term noise** (SmartTune `DTermNoiseAnalyzer`): D-term RMS, D/P ratio (D/P>0.5 → POOR, cut D_min; D/P>0.3 → MARGINAL, lower D-term LPF), D_min-activation heuristic (fraction of samples where \|D\| < 0.6×median), high-frequency energy ratio (FFT of D-term, power above fs/8 vs total).
- **Filter transmission** (PID-Analyzer): ratio of post-filter to pre-filter (debug-channel) noise spectrum, throttle-weighted.
- **RPM-filter effectiveness**: SmartTune's approach is explicitly shallow — it does not correlate actual per-motor eRPM/DShot-bidir telemetry with noise peaks (its BBL parser doesn't extract an eRPM field); it only infers "RPM filter enabled" from config flags and does a local-maxima scan for residual peaks in the 80-400Hz motor band against a noise floor. **We should do better**: parse actual eRPM/DShot-bidir telemetry from the log when present and directly correlate measured per-motor frequency against residual noise peaks, rather than inferring from config flags alone.

**Our approach**: Adopt SmartTune's D-term RMS/D-P-ratio/HF-ratio metrics with its thresholds as a starting point (to be validated against real logs before trusting numerically), adopt PID-Analyzer's filter-transmission-ratio concept, and build a genuine telemetry-correlated RPM-filter analyzer rather than reusing SmartTune's config-flag-only heuristic.

## Tracking Metrics

- **PIDtoolbox (`PTplotPIDerror.m`)**: PID-error (gyro − setpoint) histogram, peak-normalized, `std()` as a "looseness" scalar; two-sample Kolmogorov-Smirnov test (`kstest2`/`scipy.stats.ks_2samp`) between two logs' normalized error distributions to flag statistically significant tuning differences (p≤0.05); stick-deflection-binned mean-absolute-error (10%, 20%, ..., 100% of max \|setpoint\|) with SEM, showing tracking-error growth vs. maneuver intensity.
- No other project studied computes an equivalent tracking-distribution metric.

**Our approach**: Adopt PIDtoolbox's full tracking-error toolkit directly — histogram + KS-test for A/B tune comparison, stick-deflection-binned MAE for characterizing tracking degradation under load. This is directly portable to `numpy.histogram` + `scipy.stats.ks_2samp`.

## PID Recommendation Strategies

**Framing, up front (applies to everything below)**: every recommendation-engine reference studied is either an unvalidated hobby project, a project not yet hardware-validated by its own admission, or — in the case of the historical Cleanflight autotune and even the still-unreliable 2026 official Betaflight chirp autotune — a documented cautionary tale (dangerous/removed; zeroed pitch gain on a real test run, respectively). **None of this is authoritative.** Per the project brief: study for ideas, never port numbers, never auto-apply.

- **FPVtune**: opaque neural net (28 features → 3 dense layers → 18 PID outputs); no published rules; explicitly abandoned an interpretable rule-based approach for falling apart on edge cases. Not usable as a source of concrete heuristics — only as a feature-list reference (FFT noise, step response, PID-error tracking, filter performance, prop-wash detection, motor thermal prediction).
- **FPVPIDlab** (most concretely documented rule engine found — see [`reference-analysis.md`](./reference-analysis.md#6b-fpvpidlab) for full detail): overshoot/rise-time/ringing/steady-state-error thresholds mapped to specific P/D/I/FF adjustments, gated by a **D-first ordering** (raise D before ever lowering P; only reduce P when overshoot is extreme or D is already near ceiling), a **damping-ratio (D/P) clamp** (0.45-0.85, relaxed for micros), and a **D-effectiveness gate** (blocks raising D into noise, redirects to filter tuning instead). Rules shift by declared flight style (Smooth/Balanced/Aggressive) and are anchored deterministically to the log-header PID values, not live FC state, for reproducibility.
- **`bf_controller_tuning`** and **official 2026 chirp autotune**: frequency-domain, system-ID-based (phase margin, bandwidth, DC gain) rather than rule-of-thumb. `bf_controller_tuning` is fully manual (human designs the controller from the identified plant); official autotune attempts automatic PID suggestion from the same data but has documented failures.
- **Historical Cleanflight autotune**: closed-loop, in-flight, no independent verification step — removed for being actively dangerous. The clearest possible argument for *never* closing this loop live.

**Our approach**: Structure our recommendation engine around FPVPIDlab's pattern — ordered rule application (fix filters/noise before touching D; raise D before lowering P; only cut P as a last resort), D-effectiveness gating tied to our own noise metrics (above), and damping-ratio sanity bounds — but derive our own thresholds from validation against real logs and cross-checked against the official Betaflight PID Tuning Guide, rather than porting FPVPIDlab's specific numbers uncritically (per its own "not yet hardware-validated" status). Never implement closed-loop in-flight adjustment.

## Confidence Strategies

- **PIDtoolbox / PID-Analyzer**: none — purely visual, human interprets the plots.
- **SmartTune CLI**: none found — outputs metrics and grades (EXCELLENT/GOOD/MARGINAL) but no unified confidence score.
- **FPVPIDlab**: qualitative High/Medium/Low tags per rule, downgraded by a **0-100 "data quality score"** computed from segment count (20%), hover duration (35%), throttle coverage (25%), segment type (20%), tiered excellent(80+)/good(60-79)/fair(40-59)/poor(<40) — fair/poor flights force lower confidence and flag insufficient data or wind disturbance.

**Our approach**: Adopt FPVPIDlab's data-quality-score pattern (weighted combination of segment count, flight duration, throttle/stick coverage) as the basis for a confidence score that gates how strongly (or whether at all) a recommendation is surfaced — this is the only concrete, reusable confidence-scoring pattern found across all references.

## Safety Strategies

Cross-project safety patterns worth adopting, and the incidents that motivate them:

- **Bounds/clamps**: FPVPIDlab's size-aware P/I/D ranges and D/P damping-ratio clamp — bound every recommended change to a sane range regardless of what the raw metric-driven rule would otherwise suggest.
- **Effectiveness gating before amplification**: FPVPIDlab's D-effectiveness gate (don't raise D into noise; fix filters first) — a general pattern of blocking a recommendation category when the underlying signal quality doesn't support it.
- **Deterministic anchoring**: FPVPIDlab anchors recommendations to the Blackbox header's logged PID values (not live FC state) specifically so re-analyzing the same log always produces the same result — worth adopting to avoid recommendation drift/non-reproducibility.
- **Rollback**: FPVPIDlab's automatic pre/post-tuning config snapshots — we should snapshot the FC's full config (`diff all`) before writing any recommended change, and make restoring that snapshot trivial.
- **Mandatory human review**: FPVPIDlab requires explicit user review before "apply," shows a CLI diff before any command is sent to the FC, and requires a verification flight in its wizard flow. The official 2026 Betaflight autotune's own community guidance echoes this: "read the recommendations manually, cross-check them against the graphs, then make deliberate changes — never apply blindly."
- **Never close the loop live**: the historical Cleanflight in-flight autotune (rotate → measure oscillation → adjust PIDs → repeat, all in-flight, no verification) was removed for being "actively dangerous." The 2026 official chirp autotune — built with a legitimate system-ID technique, by the Betaflight team itself — still produced a test run that **zeroed out pitch gain and broke takeoff**. Two independent, authoritative failure cases converge on the same conclusion: **automated PID recommendation must be advisory-only, with mandatory human review and a real test flight before trusting any change**, regardless of how rigorous the underlying measurement technique is.
- **Version/target safety**: from the official-docs research — never replay hardware/target-specific CLI commands (`resource`, `timer`, `dma`, `motor`, `servo`) across different boards; never blind-paste a config diff/dump captured on one Betaflight version into a different version; detect firmware version and validate every CLI parameter against that version's actual schema before writing it.

**Our approach**: All of the above become explicit, non-negotiable requirements for our safety layer — not aspirational goals. Specifically: (1) recommendations are always advisory text + a proposed CLI diff, never auto-applied; (2) every recommendation carries a confidence score and is bounded by size/type-aware clamps; (3) config is snapshotted before any write, with one-click restore; (4) CLI writes are validated against the connected FC's detected version/target schema before being sent; (5) the UI requires an explicit user confirmation step, and should encourage (not silently skip) a verification flight after any PID/filter change.
